# Localization

The official app languages are **English** (`en`) and **简体中文** (`zh-CN`). Before sign-in, the browser's supported preference decides the language; without a supported preference, English is used.

## Choice and persistence

- The selector appears at the start of the basic settings assistant, once wallet, device, private profile and vault are ready. Choosing another language saves it before reloading; the assistant returns in the chosen language.
- Profile → Privacy offers a later change. The write must finish before the screen refreshes. Calls, recordings, requests and drafts use the existing refresh guards.
- The preference lives in its own encrypted `settings` record, with the entity derived from `['0xdmme-app-language', 1, accountId]`, the stable label `0xdmme:language:v1` and the value `{ version: 1, language }`. Do not change earlier account-settings records: older readers require exact keys.
- Choosing a language is independent of finishing or skipping the other basic settings. A missing record is never invented to close the assistant. Invalid language content and an incomplete vault raise errors.
- On another device, load the choice together with the settings. If work is in progress, keep the preference locally for the next start and keep the current screen language until a safe refresh.
- `0xdmme:language` in the browser and `/.0xdmme/language-preference` in the preferences cache store only the language, without account, wallet, keys or messages. The worker reads that copy when presenting push notifications. Failures never simulate a successful write.

## Catalog and keys

`src/shared/i18n/catalog.ts` holds static text, templates, accessibility labels and errors. Each entry is `key: [English, Simplified Chinese]`.

- **A key is its English text** (`'Save profile'`), or an `area.name` identifier when the same English text needs different translations or context (`'community.post-action'`, `'ranking.growth-up {0}'`). Never add keys in another language.
- `t(key, values)` translates only app templates. Interpolated values (`{0}`, `{1}`…) are preserved and never translated again.
- Static HTML is written in English and translated by `staticText()` once, before any account data enters the document. Dynamic user content is never observed or retranslated.
- Server and library errors keep their wire format: the server sends the English text, and `translatedError()` maps known reasons, numeric details and bounded diagnostics to the current language. Unknown external errors get a generic message in the chosen language, without provider payloads.
- `src/tools/localization-exemptions.ts` lists the few legacy keys outside this rule: English wire reasons whose display text differs, and labels persisted in existing records. Renaming a persisted label needs its own data migration.
- Never translate user-authored messages/posts, names, interpolated user values, technical identifiers, storage keys or persisted/wire formats.

Dates and locale formatting use the current language. The KLIPY catalog receives `en_US` or `zh_CN`, preserving the permission and the external-media contract. Generic notices and public activity titles are translated by the worker; post text and author identity stay as received. For media-only posts the server sends an empty preview and the worker picks the notice in the local language. Never use a server sentence as a marker: a person may write exactly that sentence and it must stay intact.

## Emoji

Names, keywords and accessibility labels of the 3,963 emoji use the original CLDR 48.2.3 English/Chinese annotations under the Unicode-3.0 license. The 19 sequences without artwork remain available; symbols, variants, SVGs and the original graphics package are unchanged. Search data never leaves the device. Provenance and hashes are in [vendor/emoji/README.md](../vendor/emoji/README.md).

## Build

The build splits the interface catalog and the emoji catalog into public, hash-named modules. Each module contains both languages and is part of the offline shell, so no distinct network request reveals the chosen language. The classic service worker keeps the texts it needs inlined. Asset, package and install budgets and the public source contract are unchanged.

## Signed documents

Signed wallet documents are protocol data, not catalog text. Their bytes are versioned and fixed by SHA-256 test vectors; changing the interface language never changes a document, its signature or the recovery key.

- New wallet recovery configurations use protocol v3 with a validated `language` (`en` or `zh-CN`), fixed at creation from the app's current language and bound to the signed device directory and recovery derivation. Restoring always signs the original language. Mobile handoff carries the original browser's language, not the wallet browser's locale.
- Existing bilingual v2 recovery configurations and other v2 authorizations keep their exact signing bytes and HKDF context. Do not rewrite, erase or automatically migrate them.
- Sign-in stays canonical English SIWE ([EIP-4361](https://eips.ethereum.org/EIPS/eip-4361#message-fields) requires an ASCII statement), with a full explanation in the interface language shown before the signature.
- Changing the wording or language of a signed document requires its own explicit review and a versioned migration.

## Chinese line breaks

Chinese may break between any two characters, so a squeezed flex item could shrink a short label to one character per line. `src/client/language/line-breaks.css` applies only under `:lang(zh)`: compact controls (buttons, menus, links, tabs, labels, badges, counters and chips) keep each run of Chinese whole like an English word and still break when that run alone cannot fit; headings and paragraphs avoid a single character on the last line, and small captions split into even lines. English layout is unchanged.

## Checks

`npm run i18n:check`, part of `npm run check` and CI, verifies missing entries, the key rule above and untranslated authored text outside the catalog. Exceptions are identifiers, persisted labels and specific signed statements, each with an explicit reason. Before declaring an app-facing change complete, inspect the affected visible, accessibility and error states in both languages and check responsive layout where text changed.
